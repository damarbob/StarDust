# Testing StarDust

StarDust is verified by a **smoke suite that runs against a real MySQL** — there are no mocked databases. Every behavioural guarantee below is checked end-to-end on a live 8.0.13+ server (the CI service container, or your local one).

If you just want to *use* StarDust, you don't need this file — start with the [README](README.md). This is for contributors and anyone who wants to understand exactly what the engine promises and how each promise is proven.

## Running the suite locally

```bash
composer install
cp phpunit.xml.dist phpunit.xml         # gitignored; edit with your DB creds
vendor/bin/phpunit --testsuite Smoke
```

`phpunit.xml.dist` ships with empty `<env>` placeholders for `STARDUST_TEST_DSN`, `STARDUST_TEST_USER`, and `STARDUST_TEST_PASS`. Fill them in on your local `phpunit.xml` copy (which is gitignored). A shell-exported env var with the same name still wins over the file value, so the one-off form also works:

```bash
STARDUST_TEST_DSN='mysql:host=127.0.0.1;dbname=stardust_test' \
STARDUST_TEST_USER=root STARDUST_TEST_PASS=root \
vendor/bin/phpunit --testsuite Smoke
```

The suite **skips** (it does not fail) when `STARDUST_TEST_DSN` / `STARDUST_TEST_USER` are unset, so a clone with no database still runs green. Point it only at a throwaway database — the bootstrap tests drop every StarDust table between runs.

Run a single class or method:

```bash
vendor/bin/phpunit --testsuite Smoke --filter SchemaBuilderTest
vendor/bin/phpunit --testsuite Smoke --filter testCreateModelIsIdempotentAndDoesNotBumpVersionOnReRun
```

GitHub Actions runs the same suite on every push, plus a second job that asserts the suite **fails** against MariaDB (the rejection is a feature, not a bug — see the README's Requirements section).

## What the suite covers, phase by phase

- **Phase 0 — environment.** Server is MySQL (not MariaDB), version is 8.0.13+, common table expressions work, and functional unique indexes enforce the partial-uniqueness invariant the schema registry depends on. (`EXPLAIN ANALYZE` is an 8.0.18+ operator-runbook tool and is deliberately **not** smoke-tested.)
- **Phase 1 — bootstrap.** The migration runner creates every data plane, registry, and operational table on a blank database; re-runs are non-destructive; the `stardust_schema_version` singleton is seeded with `id = 1`; the `stardust_slot_assignments` status ENUM rejects out-of-band values; the partial unique index on `field_id` is enforced at the database level; and the tenant-scoped composite indexes on `entry_data` are present.
- **Phase 2 — slot & page system.** Page provisioning emits composite `(tenant_id, slot_column)` indexes only for the filterable slots named by the caller; **the page is created with exactly those columns and its slot inventory names the same set**, one `free` row each, in the same registry transaction as the `stardust_schema_version` bump — so every free slot the capacity reporter counts is one a reservation could take, checked both against a directly provisioned page and against one a real Watcher tick produced; an empty column list is rejected, since a page with no slots would never clear the low-capacity trigger; a page provisioned in the pre-0043 sixty-column shape still reports its unindexed inventory as unclaimable, which stays true for as long as such pages exist; a forced failure rolls the registry transaction back without leaking partial inventory; sequential calls assign monotonic page numbers; the slot reserver performs the `free → assigned` transition atomically and returns `null` when no free slot of the requested family exists; and the `EmptyTableGuard` rejects DDL against populated pages before any metadata lock is acquired. Reservation is also model-affine: it prefers a page already hosting a live slot of the same model (a `backfilling` sibling counts, a `tombstoned` one does not, and another model's slots never do), spills to global-oldest when that page has no free slot of the family so a reservation that would succeed never fails, yields to `requireIndexed` because eligibility outranks ordering, stays deterministic across repeats, and reports the outcome on the existing `slot_reserved` event. Two further properties are proven rather than assumed: a held reservation leaves the model's live sibling slots writable from a second connection on a 1 s lock timeout (the ADR-normative non-locking invariant), and a model already living on a newer page stays at `excess_pages = 0` when grown while the oldest page still has capacity — measured with the spread sampler, and confirmed to fail when affinity is disabled.
- **Phase 3 — write path.** Single-entry writes commit `entry_data` + every live-slot row + (optionally) a `stardust_sync_queue` enqueue in one transaction; the exhaustion-fallback path keeps the write succeeding when slots are missing; uncoercible payload values roll the whole entry back; bulk ingest chunks transactions per `BulkIngestOptions::$chunkSize`, applies the inter-chunk delay only between chunks, and rolls each failed chunk back atomically while later chunks continue; the 1 000-entity synchronous threshold throws `PayloadTooLargeException`; async submission writes a payload artifact under `Config::$artifactDir`, inserts a `stardust_import_jobs` row, and returns an `ImportJobId`; retrying with the same `(tenant_id, idempotency_key)` returns the existing job ID; `tenant_id <= 0` is rejected before any SQL. `getImportJob()` resolves that ID back to a job: it is tenant-isolated (returns `null` for a cross-tenant or missing ID rather than throwing), its `entriesWritten` / `chunks` are checked against a **real** work-source drain rather than a hand-seeded row, a failed job still reports the last committed `entriesWritten` as the replay boundary, and a job that failed before any chunk committed reports `null` rather than `0` — the distinction an operator needs to tell "nothing ran" from "ran and wrote nothing".
- **Entry update & soft delete.** `updateEntry()` rewrites the JSON payload and the indexed slot together so a filter follows the new value and stops matching the old; **omitting a field clears its slot column** and makes the old value unreachable by filter (the full-replace invariant, and the case the feature exists to get right); an explicit `null` is kept in the payload and clears the slot too; `model_id` and `created_at` survive an update; a soft-deleted, foreign-tenant, or missing entry throws `EntryNotFoundException` and mutates nothing; an uncoercible value rolls the whole update back; introducing an unmapped filterable field enqueues for backfill instead of failing. `deleteEntry()` removes the entry from point-read, filtered read, search, and export pagination while leaving its siblings readable; a second delete returns `false` without overwriting the original timestamp or re-emitting an event; slot values are deliberately retained.
- **Phase 4 — read path.** Filters on `is_filterable = false`, `backfilling`, `tombstoned`, or unmapped slots are rejected pre-flight with a typed exception and a `pre_flight_rejected` log event — `EXPLAIN` for an accepted filter shows an index range scan on the `(tenant_id, slot_column)` composite, never a full table scan; cursor pagination over a mutated dataset never duplicates or skips entries that existed before page 1; the trailing page returns a null next-cursor sentinel; `tenant_id` outside `[1, 2^63-1]` is rejected before any SQL; rows from other tenants never appear regardless of filter collision; a field whose slot is `backfilling` returns the value from the JSON payload and never touches the slot column; the schema-version cache emits `cache_miss` on registry-version bumps and reuses the snapshot otherwise.
- **Phase 5 — resilience daemons.** The Watcher provisions a new `entry_slots_page_N` (and its 60 slot rows) when global capacity is below the threshold, bumping `stardust_schema_version.version` in the same transaction; `poll_started` / `provision_complete` / `poll_complete` events fire with `source: 'watcher'`. When a sibling session holds `GET_LOCK('stardust_page_provision', …)`, the Watcher emits `lock_contention` and does not provision (end-to-end test runs with a 1 s timeout via `Config::$watcherProvisionLockTimeoutSeconds` — production stays at 10 s). How many columns a new page indexes is proven to come from `Config::$pageIndexHeadroom` end to end, asserted against `information_schema` on the page the daemon actually created and driven through `StarDust::watcher()` rather than a hand-built `Watcher` — that factory is called by no other test in the suite, so a wrong field name in it would otherwise go unnoticed; the shipped default is read by *omitting* the parameter, so moving it fails the test, and a raised value plus a zero value are asserted alongside it because a single case cannot tell a live wire from a literal. The point of that headroom is proven by its own outcome rather than by its arithmetic: three fields of one model promoted **one at a time**, each with its own Watcher tick and Reconciler drain, end on a single page with `excess_pages` at zero and at least one reservation reporting `co_located` — the affinity outcome that was unreachable while pages were sized to demand. Promoting them together would land on one page regardless, so the fixture is deliberately serial; validated by dropping headroom to zero and confirming both halves fail, the first with three pages. The PID-file guard throws `WatcherSingletonViolationException` on contention and preserves the last PID after release. The `PollLoop` surfaces SIGTERM / flag-file shutdown within one sleep slice. The cardinality sampler emits `cardinality_sampled` (and `low_cardinality_index` when distinct/selectivity floors are breached) with `source: 'registry'`. A single advisory timer drives both samplers: the tick that fires `cardinality_sampled` fires `spread_sampled` too, and the tick that fires neither fires neither. The spread advisory measures, per model, how many distinct extension pages its live filterable slots occupy against the fewest it could occupy — `backfilling`, `tombstoned`, and grandfathered non-filterable slots are all excluded from both the page count and the slot count; `high_spread_model` fires only when the model occupies at least two pages *and* at least `spreadExcessPageThreshold` more than its minimum; the minimum is a max over slot families, never a sum, so a model at its ceiling reports zero excess; that minimum is read off what the model's own pages can actually hold rather than off the page layout, proven both DB-free (uniform pages reduce to the published division, roomiest pages are counted first, and free capacity on a page the model has never touched cannot lower the floor) and end to end, where `k + 1` and `2k + 1` filterable string fields promoted **one at a time** through real Watcher and Reconciler ticks land on the fewest pages that can hold them and report zero excess, fire no `high_spread_model`, and plan a compaction no-op — all three of which were red beforehand, reporting a floor of one page against layouts that were already optimal; and a completed retype publishes a one-shot sample with `trigger: post_relocation` while a retype still mid-backfill publishes none. The sync-queue work source drains a chunk via `SELECT … FOR UPDATE SKIP LOCKED` and routes `EntryDataMissingException` to `stardust_reconciler_dlq` with `reason='missing_entry_data'`. When the entry's filterable field still has no live slot it rolls the chunk back and then reserves one: with an indexed free slot available the tick emits `slot_reserved` and no `capacity_wait`, the field's assignment goes to `assigned`, the Watcher's pending-demand count drops to zero, and the next tick drains the queue row and writes the value into the slot column; with only *unindexed* free slots, or none at all, no reservation is made and the tick emits `capacity_wait` and rolls back exactly as before. A non-filterable field acquires no slot on either path. Model compaction is proven by its own success criterion rather than by internal branches: a model deliberately fragmented across three pages, compacted through the real service, ends on one page with `excess_pages` at zero and every value intact — and the fixture is asserted to start fragmented, so the test cannot pass on a model that was already compact. Alongside it: a same-type retype is proven to relocate every value to a different slot column across all four declared types while leaving the field's shape untouched; re-running a compaction on a compact model plans nothing and bumps no schema version; `--dry-run` leaves every slot row byte-identical and emits no event; an inadmissible plan throws before any mutation, leaving slots, checkpoints and the version unchanged; compaction refuses outright — `--dry-run` through the real facade included — while a field of the model is still mid-lifecycle, whether that field is mid-relocation or merely mid-promotion, and a refusal leaves every slot byte-identical and emits nothing, while the same model compacts cleanly to `excess_pages` zero once the Reconciler drains it (the fixture is first proven genuinely half-relocated, and the whole group was validated by neutering the guard and confirming four of the six fail); and the planner's own arithmetic — minimal page set, no-op detection, family ceilings, per-family starvation, and the double-occupancy rule that free capacity never counts a slot the plan is about to vacate — is covered DB-free. Slot reservation is also proven honest under `ERRMODE_SILENT`: a refused claim returns `null` rather than a `SlotAssignment` for a slot it never took, leaves the field on exactly one live slot, and does not bump `stardust_schema_version`. The import-job work source claims one pending row, decodes the single-document JSON artifact, materialises entries through `EntryWriter::writeWithinTransaction()` in chunk windows paced by `Config::$reconcilerInterChunkDelayMicros`, and transitions to `completed | failed` with a manifest. That manifest is proven to enumerate each chunk: a five-entry import at two per chunk records three chunks whose sizes and entity id ranges are asserted against the ids `entry_data` actually assigned, not against an expected sequence; a chunk that fails appends exactly one terminal `failed` record with a null id range while leaving the committed `chunks` / `entries_written` boundary untouched; a failure on the *first* chunk omits the counters rather than writing them as zero, so the consumer-facing `null` ("nothing committed") stays distinct from `0`; a malformed artifact leaves the column NULL entirely; and a re-claimed job appends to the prior worker's records with the chunk index continuing rather than restarting, including the counters-only manifest shape every in-flight job carries across the upgrade. The whole group was validated by neutering the two record appends and confirming seven of the new assertions fail. `Reconciler::tick()` itself ticks work sources round-robin, short-circuits on `CAPACITY_WAIT`, and paces between `WORK_DONE` outcomes using the same inter-chunk delay. The DLQ replayer re-enqueues by id or by reason in a single transaction and throws `DlqReplayNotFoundException` on no-match. Lock failures no longer kill the daemon: with errno **1205** injected into the slot UPSERT, a chunk that loses a lock once retries and still commits, and one that loses it for the whole budget **returns** `LOCK_WAIT` with a `lock_wait` event and a byte-identical checkpoint rather than throwing — proven at the daemon boundary by driving the real `Reconciler` under the real `PollLoop` and asserting `run()` returns. Two narrower assertions cover the two sources that failed differently: a sync-queue lock failure writes **no** DLQ row and leaves the queue row claimable (it used to quarantine the entry as `reason: 'other'`), and an import-job lock failure leaves the job `processing` with its manifest intact rather than `failed` with `entry_write_failed`. Validated by removing the retry wrapper and confirming three of the five fail, the `PollLoop` one with the exception escaping through `Reconciler::tick()`. A closed-vocabulary guard greps `src/Watcher/`, `src/Reconciler/`, and `src/Liberator/` for `'event' => '...'` literals and asserts the union matches the documented allowlist.
- **Phase 6a — slot reclamation (Liberator).** Tombstoning a slot and starting the Liberator nullifies every non-NULL value in the corresponding `entry_slots_page_N.<slotColumn>` across the partition, transitions the registry row from `tombstoned → free` (and clears `field_id`) in the same transaction as the final chunk's nullification, and bumps `stardust_schema_version.version`. Sweep proceeds in `LIMIT N` chunks; each chunk's `UPDATE` and the `sweep_cursor_id` advance commit together, so a mid-sweep crash resumes deterministically from `last cursor + 1` on restart. On `SQLSTATE 40001` (InnoDB deadlock) the sweeper rolls the chunk back, emits `deadlock_retry`, and retries the same chunk from the same cursor; after three consecutive deadlocks on the same chunk it advances past **that chunk** — `max(the chunk's last id, cursor + chunkSize)`, so the skip is a number of rows rather than a span of ids — increments `sweep_gap_count`, emits `sweep_gap_flagged`, and continues, so bounded contention does not block sweep progress indefinitely. Proven on a deliberately sparse page: two populated chunks produce exactly two gaps, where the id arithmetic produced 101 and a `sweep_gap_count` to match. **A sweep that abandoned a chunk does not reclaim** — while a gap is outstanding every commit pins `sweep_cursor_id` at the first gap, the slot stays `tombstoned`, and no `sweep_complete` is emitted; a following pass with the contention gone clears the skipped range and only then transitions to `free`. Pinning on every chunk rather than rewinding at the end is asserted on the event stream, because a completed pass hides the difference — the exposure is a daemon killed mid-pass, which would otherwise restart past the skipped rows and reclaim over them. The gap path also performs no write of its own: the counter rides the next chunk's commit, and a lock failure in a dedicated gap transaction used to escape the retry budget and kill the daemon, which is asserted by driving a sweep whose every registry write fails and requiring it to return. Both halves are asserted, including that the slot is still `tombstoned` with its ten un-nullified rows after the gapped pass. Tombstoned slots are processed `tombstoned_at ASC, page_id, slot_column` (deterministic across restarts). **A slot that has been round the lifecycle before sweeps from the beginning of the page, not from its previous occupant's cursor:** the UPDATE that flips a slot to `tombstoned` clears `sweep_cursor_id` and `sweep_gap_count`, while the `tombstoned → free` reclaim preserves both, so the annotations always describe the sweep that produced the current state. Proven end to end through the facade — promote, demote, sweep, promote onto the recycled slot, backfill, demote, sweep — asserting the reclaimed column holds none of the previous field's twenty values; before the reset landed all twenty survived, with `sweep_chunk` and `sweep_complete` both reporting honestly for the empty range they walked. The same reset rides on the model purge's final-chunk severance re-assertion, and its status guard is separately asserted not to restart a sweep already in flight. The PID-file guard throws `LiberatorSingletonViolationException` on contention. Closed `source: 'liberator'` event vocabulary: `sweep_started` (per non-empty batch only — idle ticks emit nothing), `sweep_chunk`, `sweep_complete`, `deadlock_retry`, `sweep_gap_flagged`. The bootstrap migration adds the `sweep_gap_count INT NOT NULL DEFAULT 0` column idempotently.
- **Phase 6b — field retype & filterability promotion.** `retypeField()` atomically updates `stardust_fields.declared_type`, tombstones the field's current live slot, reserves a new `backfilling` slot of the target type (or defers if no matching free slot exists), bumps `stardust_schema_version`, and inserts a `running` `backfill_checkpoints` row keyed `retype_field_{id}` — emits `retype_started`. `numeric ↔ datetime` and `int ↔ datetime` retypes raise `IncompatibleRetypeException` at registry-write time with zero registry mutation. Filterability promotion follows the same pipeline but the new slot reservation demands a column with a `(tenant_id, slot_column)` composite index. While the slot is `backfilling`, reads of the field fall back to the JSON payload and filter queries throw `FieldNotIndexedException`. The Reconciler's third work source — `RetypeBackfillWorkSource` — claims one running checkpoint per tick via `SELECT … FOR UPDATE SKIP LOCKED`, runs the normative type-coercion matrix per row through `JSON_EXTRACT`, writes coerced values (or NULL on uncoercible) via `INSERT … ON DUPLICATE KEY UPDATE`, and on the final chunk transitions the slot `backfilling → ready` plus bumps `stardust_schema_version` in the same transaction. Per-row uncoercible values emit `coercion_null` with the closed taxonomy (`out_of_range`, `non_integer`, `malformed_datetime`, `malformed_number`, `epoch_coercion_rejected`, `unparseable`); absent/null JSON values do NOT emit (only attempted-and-failed coercions are observable). Promotion to `ready` emits `promote_to_ready` and triggers `CardinalitySampler::sampleSlot()` for the one-shot post-backfill `cardinality_sampled` event with `trigger='post_backfill'`. Idempotent resume: mid-chunk crash + restart re-processes only entries after `last_processed_id`, and the UPSERT primary key guarantees no double-write. The bootstrap migration adds the `source_declared_type VARCHAR(16) NULL` column to `backfill_checkpoints` idempotently. A field is also proven not to be a one-way door: after a promotion drains, a demote-then-promote cycle reopens the same checkpoint rather than colliding on `ux_backfill_job_name`, the reopened row restarts at cursor 0 with `completed_at` cleared, and — the assertion that actually discriminates — it carries the *second* lifecycle's `source_declared_type`, not the first's. `CompactModelTest` covers the same property end to end: a model that is re-fragmented after a successful compaction compacts again, relocating a field that already moved once. Both were validated by neutering the upsert and confirming they fail with errno 1062. A concurrent second initiator is refused rather than silently resetting the live checkpoint, because the field read now runs `FOR UPDATE OF f` inside the initiation transaction; `RetypeInitiatorConcurrencyTest` proves that read is a locking one by holding the row from a sibling session and asserting an ADR 0024 categorical rejection *cannot* be reached — the one shape that resolves between the read and the reservation, since the reservation's FK parent-row lock blocks a sibling regardless and so cannot discriminate.
- **Schema introspection.** `listModels()` is ordered by id and scoped to the tenant, returning an empty list rather than another tenant's models; `describeModel()` reports fields in registration order with their declared types, and returns `null` for a missing model or one belonging to another tenant. The `isFilterable` / `isIndexed` split is pinned across all four states that distinguish them: a reserved filterable field is both; a JSON-only field is neither; a filterable field still awaiting capacity is declared-but-not-indexed; and a `backfilling` slot does **not** count as indexed, matching ADR 0004's refusal to filter against one. `indexedFields()` returns only the queryable subset, and `demoteFieldFromFilterable()` is reflected immediately — no backfill window to wait through.
- **Phase 7 — async exports (Chronicler).** `submitExport()` enforces the per-tenant active-job cap atomically (`SELECT … FOR UPDATE` + `INSERT` in one transaction) and emits `export_accepted` (source `export_api`); a 4th concurrent submission for the same tenant throws `ExportJobActiveCapExceededException`. A sibling-session test holds `SELECT … FOR UPDATE` on the tenant's active range while a second submitter runs with `innodb_lock_wait_timeout = 1` — the second submission blocks, surfaces `SQLSTATE 1205`, and proves the cap check is genuinely serialised across sessions (no phantom inserts past the cap). `getExportJob()` is tenant-isolated — returns `null` for cross-tenant or missing job ids. The Chronicler's per-tenant round-robin claim orders pending jobs by `MIN(created_at) GROUP BY tenant_id`, computed at claim time without a materialised column — a single tenant's burst cannot starve another tenant's oldest job. Two-session `SKIP LOCKED` tests prove the claimer skips rows held by a sibling `FOR UPDATE` and routes to the next available row; two parallel claimers never double-claim the same id. Abandoned-claim sweep detects stranded `processing` rows with `heartbeat_at < UTC_TIMESTAMP() - INTERVAL leaseTimeoutSeconds SECOND`, best-effort deletes the prior partial, and resumes from `last_cursor` with `claimed_at` preserved. Lease-loss self-detection at every chunk commit (`WHERE worker_identity = self`, `rowCount() == 0` ⇒ `lease_lost` + delete partial, no terminal-state mutation). End-to-end CSV happy path covers RFC 4180 quoting (comma, double-quote, CR, LF), `\r\n` line terminator, header derived alphabetically from `stardust_fields`, and embedded-NUL → `row_skipped{format_invalid}`. End-to-end JSON happy path validates the streamed single-document array (leading `[`, `,`-prefix for subsequent rows, trailing `]`, exactly `n-1` commas for `n` rows, round-trip through `json_decode`). Three-deadlock budget per chunk → `chunk_skipped{cause:deadlock_budget_exhausted}` + cursor advance + `skip_count += pageSize` (simulated by a reflection-bypass `DeadlockInjectingPdo` that wraps the test connection and throws `SQLSTATE 40001` on the `entry_data` SELECT); skip-cap (1 000) trip → `failed:excessive_skips`; ENOSPC short-write during artifact append (exercised via a `failwrite://` stream wrapper that returns 0 on every `fwrite`) → `failed:disk_full` + `job_failed{reason:disk_full}` — also covers the header-write disk-full path on `stream->open()`; partial-artifact bytes > 5 GB cap → `artifact_oversized` (distinct event) + `failed:artifact_size_exceeded`; idle ticks GC TTL'd completed artifacts (24 h) and orphaned failed-job partials (1 h); pre-claim disk-pressure gate emits `low_disk` and skips new claims while in-flight jobs continue. Tenant isolation is enforced by the pager's `WHERE tenant_id = ? AND model_id = ? AND deleted_at IS NULL` predicate; soft-deleted rows never appear in artifacts. The closed-vocabulary guard scans `src/Chronicler/` and `src/Export/` for `'event' => '...'` literals — adding an unallowlisted name fails CI.
- **Sort ordering.** A read with no sort returns insertion order and emits a byte-identical pre-sort cursor, so nothing that paginated before changes. Ordering works on every slot family — strings lexically, ints numerically rather than lexicographically, numerics and datetimes by value — plus the two intrinsic targets, entry id and creation time, in both directions. Ties fall back to entry id *in the sort's own direction*, which is what makes each ordering total. Entries with no value for the sort field sort first ascending and last descending and are never dropped from the page, including entries that have no extension-page row at all — the sort's page join is `LEFT`, and that test was validated by switching it to `INNER` and confirming it alone goes red. Sorts on unknown, non-filterable, and `backfilling` fields are rejected pre-flight exactly as the equivalent filters are, and sorting stays tenant-isolated. Walking a sorted result set two rows at a time reproduces the single-page ordering exactly — no row skipped, none repeated — across ties that span a page boundary and across a NULL block wider than one page; deleting the keyset predicate's NULL branch makes an ascending walk stop dead at the end of that block, which is how the branch is known to be load-bearing. Strings that differ only past MySQL's 1024-byte `max_sort_length` still order and paginate correctly, since ordering on a TEXT slot proved exact on 8.0.13 rather than truncated. A cursor replayed under a different sort key, or the same key reversed, is refused with a typed error instead of silently walking a different sequence. SQL-shape tests pin the rest: the sort join appears under the `EXISTS` strategy too, reuses a page the filter already joined, and the anchor lookup plus both keyset directions carry the tenant predicate.

- **Phase 8 — search driver & JSON query filter.** The `JsonFilterDecoder` turns a JSON wire payload into the closed filter AST (twelve leaf operators; full AND/OR/NOT composition), deduplicates `in` / `nin` arrays at decode time, and enforces the closed 13-code error taxonomy with RFC 6901 JSON Pointers plus payload-size, nesting-depth, node-count, argument-count, and string-length bounds — the decoder never consults the registry, so it is reusable in offline tooling. The three-stage pre-flight pipeline (field resolution → driver capability → value-type validation) rejects unknown, non-filterable, unsupported-operator, and type-mismatched filters before any SQL is issued, emitting `pre_flight_rejected` / `capability_unsupported`. The adaptive `SqlFilterCompiler` keeps pure-AND trees on the Phase 4 INNER-JOIN-per-page execution shape and switches to `EXISTS` / `NOT EXISTS` subqueries for any subtree containing OR or NOT, with tenant isolation enforced on both strategies; OR/NOT filters round-trip end-to-end against real data. A custom `EntrySearchInterface` driver injected through `Config` is invoked in place of the default `MysqlNativeDriver`, and every `search()` call emits one `search_request` event carrying `latency_ms`, `rows_returned`, `has_more`, `tree_node_count`, and `compile_strategy`. The closed-vocabulary guard extends to scan `src/Search/` and `src/Filter/`.
- **Datetime filter bounds.** The UTC offset a `datetime` bound is required to carry is now applied rather than discarded: an instant written with a non-zero offset matches a filter for that same literal (it did not before — the write path normalised and the filter path did not), and `10:00+07:00` selects the row holding `03:00Z` rather than the one holding `10:00Z`. The `Z` form, which was correct only because dropping a zero offset changes nothing, still is. `between`, `in`, and `lt` are covered separately from `eq` because they reach SQL through the compiler's list path rather than its scalar one. A fractional bound is honoured rather than floored, so `lt '…10:00:00.5Z'` still matches a stored `10:00:00`; and the naive form stays rejected with `value_type_mismatch`. Normalisation happens in two layers and **either one alone fixes the MySQL result set**, so the behavioural cases were validated by neutering *both* (four go red) and the fractional case by flooring the bound. Because of that, each layer carries its own pin: the tree leaving pre-flight is asserted to hold canonical UTC RFC 3339 rather than a MySQL literal, since that is what a third-party driver receives, and the compiler's fragment is asserted to bind the MySQL literal rather than the RFC 3339 form — the conversion that keeps `Warning 1292` out of the emitted SQL. That second one asserts on the binding rather than on `SHOW WARNINGS`, which the suite's native-prepare connection cannot read back: the statement is unsupported in that protocol and replaces the list it was going to read. The warning's absence was verified directly against 8.0.13 instead.

## Helpers

- **`SchemaBuilder`** (`tests/Smoke/Schema/SchemaBuilderTest`) — the model/field registration helper is get-or-create and bumps `stardust_schema_version` exactly once per inserting call. Re-running with the same names returns the existing ids and does not duplicate rows or bump the version again; unknown declared types and non-positive tenants are rejected before any SQL.

## Test conventions

- Smoke tests under `tests/Smoke/` hit a real MySQL. Every test class that defines a `tearDown()` guards it with `isset($this->pdo)` because PHPUnit still calls `tearDown` after a `markTestSkipped()`/`fail()` in `setUp`, leaving the typed property uninitialised.
- **A test gets its clean slate from `Support\SchemaFixture::reset()`, in `setUp()`, and there is no `tearDown()` sweep.** The reset empties the tables rather than dropping them, because dropping them does not scale: 782 tests x ~22 DDL statements, each of which MySQL 8.0 commits atomically across InnoDB *and* the binlog, cost roughly 1.5 s per test — about eighteen minutes of the wall clock before a single assertion ran. `DELETE FROM` reaches the same end state in ~7 ms. Note the trap that rules out the obvious middle ground: **`TRUNCATE TABLE` is DDL in InnoDB** (it drops and recreates the tablespace) and benchmarks no better than the drop-and-rebuild it would replace. `BootstrapTest` keeps the real drop-and-rebuild, since proving that DDL idempotent and non-destructive is its whole subject.
- **`SlotSweeper`'s gap path used to depend on the fixture for its correctness, and no longer does.** It advanced past a poisoned chunk with `$cursor + $chunkSize` — arithmetic on *ids*, where ADR 0009 says skip ahead by `LIMIT` **rows** — and the two agree only while `entry_data` ids are dense and 1-based, which dropping the table used to guarantee for free. `SchemaFixture` therefore reset that counter to keep the refactor behaviour-neutral. ADR 0046 fixed the arithmetic, `entry_data` came out of `IDENTITY_TABLES`, and the suite now runs against the sparse, non-1-based ids production actually has. The episode is worth keeping in mind when reading fixtures: a counter reset that exists "for determinism" may be holding a defect still, and the test that most needed the sparse ids was the one written to prove the fix — it passed alone and failed in the suite until its `AUTO_INCREMENT` bump was made relative rather than absolute.
- Tests build on a small hierarchy of base cases: `WritePathTestCase` (connection + registry-seed helpers) → `ReadPathTestCase` → `Phase5TestCase` → `Phase6aTestCase` → `Phase6bTestCase` → `Phase7TestCase`. Extend the closest fit rather than duplicating the env-gated `setUp`. The rename, model-rename and delete suites all sit on `Phase6bTestCase` — none of them is a phase.
- `phpunit.xml.dist` sets `failOnWarning`, `failOnRisky`, `beStrictAboutOutputDuringTests`, and `beStrictAboutTestsThatDoNotTestAnything` — keep tests strict-clean.
- The table-drop allowlist is `Support\SchemaFixture::CORE_TABLES`, and it MUST include every Bootstrapper-managed table — a name missing from it survives the reset and leaks state into the next test. Both the `DELETE` sweep and `BootstrapTest`'s drop-and-rebuild read that one list, and `Conventions/BootstrapperTableAllowlistTest` fails if it drifts from the tables `Bootstrapper.php` creates.

## Field rename (ADR 0036)

`tests/Smoke/Rename/` — 28 tests over the rename lifecycle, extending `Phase6bTestCase`.

**What it proves.** `RenameInitiatorTest` pins the synchronous registry tuple: name flip, `previous_name` stashed, schema-version bump and a `running` checkpoint all commit together, with `rename_started` emitted once post-commit. It also pins the guards — foreign tenant, empty name, collision with a sibling's current name, and the case a naive implementation passes by accident: **collision with a sibling's `previous_name`**, which `UNIQUE (model_id, name)` cannot see, and which would otherwise make one field read another's values mid-drain.

`RenameBackfillTest` covers the asynchronous half: multi-chunk drain, cursor advance, idempotence over an already-migrated range, rows that never held the field left untouched, and the final chunk completing the checkpoint, clearing `previous_name` and bumping the version atomically. Its highest-value case is payload fidelity — an entry keyed `{"0":…,"1":…}` alongside nested objects, nulls, floats and non-ASCII text must survive byte-for-byte, because a decode-and-re-encode implementation would silently turn that payload into a JSON array.

`RenameWindowTest` is the one that matters most in review. It deliberately half-migrates a model and asserts that reads return the value under the *new* name for **every** row; that the point read agrees with the paginated read on the same entry; that a write or a full-replace update still using the *old* name lands under the new key and survives the rest of the drain; and that a filter on the new name works immediately while the old name is rejected outright.

`RenameConcurrencyTest` pins lifecycle exclusivity in both directions, including through `compactModel()` — which needs a deliberately fragmented model, since a model with nothing to compact would pass the test vacuously.

**Exports during a rename** are covered by `tests/Smoke/Chronicler/RenameExportWindowTest`, which extends `Phase7TestCase` and so inherits both the rename helpers and the Chronicler fixtures. It half-migrates a model, runs a real export to completion, and asserts that every CSV cell is populated for rows still on the pre-rename key — the failure it guards against is a correct header over blank cells, with no exception, no `row_skipped` and `skip_count` at zero. It also pins the deliberate asymmetry that the JSON artifact keeps emitting the old key verbatim, and that a settled rename leaves an export byte-identical to a never-renamed model's. The CSV case was validated by temporarily neutering `HeaderResolver::resolveAliases()` and confirming it fails, so it is not a fixture that could not have failed.

**Export filters** are covered by `ExportJobSubmitterTest::testNonEmptyFilterIsRejected` and `testRejectedFilterInsertsNoRowAndConsumesNoCapSlot`. The second is the one that matters: it proves the guard runs before the transaction, the INSERT and the per-tenant cap probe, so a refused submission leaves no row and costs the tenant nothing.

## Field deletion (ADR 0037)

`tests/Smoke/Delete/` — extending `Phase6bTestCase`, in four files that mirror the rename suite.

**What it proves.** `DeleteFieldInitiatorTest` pins the synchronous half: `deleted_at` set, `is_filterable` cleared, any live slot tombstoned with `field_id` nulled, terminal sibling checkpoints removed, the version bumped and a `running` checkpoint opened — all in one commit, with `delete_started` emitted once afterwards. It also pins the two return-`false` cases that are deliberately *not* exceptions (unknown field, another tenant's field, a repeat delete), and the two that are (`RenameInProgressException`, `RetypeInProgressException`). `testARefusedDeleteMutatesNothing` is the one worth reading: refusing rather than cancelling is only worth anything if the in-flight lifecycle stays drainable afterwards.

`DeletePurgeTest` covers the asynchronous half: multi-chunk drain, sibling keys and other models untouched, rows that never held the field skipped by the `JSON_CONTAINS_PATH` guard (which is what keeps `rows_purged` honest), and the final chunk hard-deleting the field row and its checkpoint together. Payload fidelity is ported wholesale from the rename suite — the `{"0":"x","1":"y"}` → `["x","y"]` trap applies to any decode-and-re-encode purge — alongside awkward field names carrying spaces, leading digits, quotes, backslashes and non-ASCII. `testTombstonedSlotStillReclaimsAfterTheFieldRowIsDeleted` reaches into the Phase 6a Liberator helpers to prove the orphaned tombstone still sweeps back to `free` with its field row already gone.

`DeleteWindowTest` is the one that matters most in review, and it opens by proving its own fixture: `testFixtureLeavesResidueInStorage` asserts that some rows really are still carrying the deleted key, because every other assertion in the file is "the API does not show this field" and would pass vacuously against a fully-purged model. On top of that it pins that the point read agrees with the paginated read on the same entry — the failure mode a naive implementation ships, since `read()` is driven by the registry snapshot and `get()` returns the payload verbatim — that a filter on the deleted name is rejected rather than quietly matching nothing, that a write still sending the name cannot resurrect the key, and that a write during the window never reserves a slot for the field (which would re-take the foreign key and wedge the final delete permanently).

`DeleteConcurrencyTest` pins the inverse guards — rename, retype, promotion and demotion all refused mid-delete — plus the name-reuse behaviour: `defineField()` raises rather than resurrecting the field being deleted, and the name frees up once the purge lands. It also pins that a deleting field registers no Watcher demand, which is the failure most likely to slip past unit-level reasoning.

Its compaction case is worth reading for what it *doesn't* assert. Written first as a copy of the rename suite's equivalent — expecting `compactModel()` to refuse — it failed, because the analogy does not hold: a renaming field keeps its live slot and stays visible to the planner, whereas a deleting field has been tombstoned *and* demoted, and `CompactionRepository` selects on both. It now pins the real behaviour: compaction ignores the field on its way out and compacts what remains.

**Not covered.** A deletion racing a concurrent Chronicler export end to end; the CSV header exclusion is asserted directly against `HeaderResolver` rather than through a live drain, and the JSON artifact's deliberate non-bridging is documented but not pinned by a test. Nor is the plan-then-delete compaction race, which is the only path by which `compactModel()` can reach the `deleted_at` guard and is not constructible single-threaded.

## Model deletion (ADR 0038)

`tests/Smoke/Delete/` again — four `Model*` files beside the field ones, plus `ModelSnapshotShapeTest`, all extending `Phase6bTestCase`.

**Why `ModelSnapshotShapeTest` exists at all.** Model deletion needed a model-level marker, and reading it meant rewriting the two queries behind every read and every write: `SlotResolver::load()` and `LiveSlotMap::loadFor()` now drive off `stardust_models` and outer-join out to the fields, because a query rooted at the fields cannot tell a model with no fields from a model that does not exist. That rewrite has two silent failure modes, and **nothing in the pre-existing suite would have caught either**. The all-null outer-join row registers a phantom field under the empty string — `stardust_fields.name` is `NOT NULL`, so `(string) null` yields `''` and passes every later check — and `ResultAssembler` then emits `'' => null` on every row of every read of that model. And selecting both `deleted_at` columns under one alias makes `FETCH_ASSOC` keep only the last, silently conflating "this field is being deleted" with "this model is". The second is only observable in the mixed case, since a real model purge sets both. Both were confirmed to fail by neutering the guards before the file was accepted.

The third thing it pins is the invariant the whole feature rests on: **a missing `stardust_models` row must never read as "deleting"**. `entry_data.model_id` is a deliberate logical-only reference, so rows whose model has no registry row are legal, and four existing fixtures build exactly that. `ModelDeleteGuardsTest::testEveryGuardIgnoresAModelIdWithNoRegistryRow` walks every guarded surface against a fabricated id for the same reason — an inner join anywhere would break all of them at once, and `EntryDeleter`'s multi-table UPDATE is the one where it would be silent (a `false` return rather than an error).

**`ModelDeleteGuardsTest`** sets the marker by hand with `markModelDeleted()` rather than running the lifecycle, which is the design's gift: the drain marker is a plain column, so the entire severance contract is testable with no purge code. It pins the write refusals (including that `bulkWrite()` refuses *before any chunk commits*, and that a refused `submitBulkWrite()` leaves no artifact on disk), the read darkening on both the filtered and match-all paths, `deleteEntry()` returning `false`, introspection, name reuse, rename, compaction and export refusal. Two assertions are negative space: `get()` must not return an `Entry` with an empty field map — the failure mode if the model check is folded into `canonicalisePayloadKeys()` instead of preceding it — and renaming *another* model onto a deleting model's name must still raise `ModelNameConflictException`, because `ux_models_tenant_name` is unconditional and the clash is real, just temporary.

**`DeleteModelInitiatorTest`** mirrors the field initiator: one atomic tuple, one `model_delete_started`, the three refusals in fixed order, and `testARefusedDeleteMutatesNothing` proving the in-flight lifecycle stays drainable. `testAFieldlessModelIsSeveredAndOpensAClaimableCheckpoint` is the one that justifies the extra column — a model with no fields marks zero field rows, so a field-derived guard cannot express its state at all.

**`ModelPurgeTest`** covers the drain: multi-chunk, page-table rows cascaded away with their entries, sync-queue rows dying in the same chunk (asserted by draining the sync queue afterwards and finding **zero** `missing_entry_data` dead-letter rows — the counter-test for the whole rule), soft-deleted entries hard-deleted too, other models and tenants untouched, and the escaped `LIKE` refusing to claim an operator-named `deleteXmodelY_rebuild` job. Two tests seed the anomalies the final chunk's severance re-assertion exists for: a slot row that has reacquired a `field_id`, and a field row that has lost its marker. Both would otherwise fail errno 1451 *after* earlier chunks had already destroyed their entries, with no dead-letter route out.

**`ModelDeleteWindowTest`** carries the vacuous-pass problem in a sharper form than the field version. A model window test can pass for free in two ways: the purge already finished, **or the model never existed** — `read()` on an unknown id returns an empty page and `describeModel()` returns null today, with no code change at all. So `halfPurgedModel()` asserts five things about its own fixture before returning (a row behind the cursor gone, a row ahead still present, the model row alive, the fields not yet cascaded, the checkpoint `running`), and `testTheDarkAssertionsCannotDistinguishAModelThatNeverExisted` records the reason as a test rather than a comment.

**`ModelDeleteConcurrencyTest`** pins the inverse guards and one race ADR 0038 does not name: a sync-queue row for a deleting model must drain as a no-op rather than writing a slot or filing a dead-letter row. `BackfillExecutor` reads `entry_data` non-locking and then UPSERTs into the page tables, so a purge committing in between produces errno 1452, which `SyncQueueWorkSource`'s catch-all files as `reason: 'other'` — the same self-inflicted DLQ noise the in-transaction sync-queue delete prevents, arriving through a different door.

**The Liberator fix ships here too.** `LiberatorDeadlockRetryTest::testLockWaitTimeoutIsRetriedLikeADeadlock` pins that errno **1205** is retried. Measured in both directions, the purge cascading `entry_data` deletes into `entry_slots_page_X` versus the Liberator nullifying the same rows produces 1205, never 1213 — and severance tombstones every slot of the deleted model, so the Liberator is *guaranteed* to be sweeping precisely those slots. `SlotSweeper` matched only 40001/1213, and `PollLoop` deliberately does not catch, so an unretried 1205 exited the daemon and crash-looped for the whole purge. Confirmed by reverting the predicate and watching the raw `PDOException` escape.

**Not covered.** The concurrent-daemon contention itself is not a smoke test — a deterministic 1205 needs two connections racing on real row locks, and the suite has no fixture shape for it. It was verified out-of-band instead: a two-page model with pending queue rows, deleted, then drained by a real `bin/stardust reconciler` and `bin/stardust liberator` running together, asserting everything gone, zero dead-letter rows, slots reclaimed to `free`, the sibling model untouched — **and both daemons still alive**. That last clause is the whole point of folding the Liberator fix in, and it is the one thing no test in this suite will tell you.

## Model rename

`tests/Smoke/Rename/ModelRenameTest` — 14 tests, extending `Phase6bTestCase`.

**What it proves.** The happy path is one UPDATE, so most of the value is in the negative assertions. `testRenameDoesNotBumpSchemaVersion` is the important one: `SchemaBuilder::createModel()` bumps when it inserts a model, so the omission here looks like an oversight unless it is pinned — nothing a cached snapshot holds changes on a model rename, and the version row is a singleton, so a bump would invalidate every model in every process for nothing. `testNothingElseMoves` covers the rest of that ground: entries read back identically by `model_id`, the slot assignment is untouched, and field names are unaffected.

`testTheSameNameInADifferentTenantIsAllowed` is the one that catches a collision check which lost its tenant predicate — the unique key is `(tenant_id, name)`, so two tenants may each own a model called `bill`. Missing-model and foreign-tenant are asserted to raise the *same* exception, so a caller cannot probe another tenant's model ids.

`testSeedingWithTheOldNameCreatesASecondModel` deliberately pins a footgun rather than a guarantee: `SchemaBuilder::findModelId()` looks up by `(tenant_id, name)`, so a seed script still naming the old model creates a second one. It is inherent to get-or-create and not fixable without changing those semantics, so the test exists to make it documented behaviour.

## Event correlation (ADR 0020)

`tests/Smoke/LifecycleCorrelationTest` — 9 tests, extending `Phase6bTestCase` — plus `tests/Smoke/Conventions/RegistryCorrelationTest` (DB-free source scan), and one test each added to `WatcherDemandDrivenProvisionTest` and `CompactModelTest`.

**Read this before writing any test that asserts on a `correlation_id`, because the obvious assertion is worthless.** `StdoutNdjsonLogger` synthesises a fresh v4 UUID for any event whose context omits one, so *every* record has always carried a well-formed id. Three existing tests asserted exactly that and passed throughout the period when nine `source: registry` sites were passing nothing at all. What has to be asserted is that two events of one operation carry the **same** id.

**What the suite proves.** All four asynchronous lifecycles — field rename, retype/promotion, field deletion, model deletion — emit their `*_started` and their completion event under one id, across the process boundary between the initiator and the Reconciler, carried on `backfill_checkpoints.correlation_id`. Each of those fixtures drives a multi-chunk drain and asserts the shared id **differs** from the tick's `chunk_correlation_id`; without that second half the test would pass for a single-chunk drain that simply reused the chunk id for both keys. Sub-events within one synchronous operation are covered too: `slot_reserved` joins the retype that reserved it, `page_provisioned` joins the Watcher tick that ordered it, and a compaction's id reaches both the `retype_started` of every relocation it orders and each relocation's own `slot_reserved`.

Two edge cases carry their own tests because both fail silently. A **second** lifecycle on the same field reuses the checkpoint row, so `insertOrReset()` must reset the column or the new drain's completion joins the *previous* start — the same trap as `source_declared_type`, and `testASecondRenameDoesNotInheritTheFirstsId` pins it. And a checkpoint opened **before** the column existed reads back null, where the work source must fall back to the chunk id rather than emit a null the ADR types as non-nullable; that fallback is what makes the `ALTER` safe under a running fleet.

**Validated by neutering**, per the `SlotAffinityTest` precedent: the work source was reverted to `$chunkCorrelationId`, and separately the upsert's `correlation_id = VALUES(correlation_id)` clause was removed, with each change confirmed to turn the relevant tests red before being restored. `RegistryCorrelationTest` was validated the same way, by stripping the id from `ModelRenamer`.

**The scan's blind spot is not hypothetical — it has already hidden a real defect.** `RegistryCorrelationTest` checks that `'correlation_id'` appears at each emit site; it cannot tell whether the *right* id was passed. `CardinalitySampler` and `SpreadSampler` sailed through it while minting their own ids inside a retype promotion that already had one, so a promotion emitted `promote_to_ready` under the lifecycle id and then four advisory events under two unrelated ones. `testThePostPromotionAdvisoriesJoinTheirRetype` is what catches that, and it was validated by neutering — with the neutered build confirmed to still pass the scan, which is the point. **A new `source: registry` event needs a behavioural assertion here as well as passing the scan.**

**Not covered.** The `api` and `bulk_api` sources have the same defect and are out of scope for this work — `entry_written` and its paired `exhaustion_fallback` carry unrelated ids, as do the chunks of one `bulkWrite()`. Recorded as ROADMAP item 26 rather than fixed here. The search path is already correct (`cache_miss` and `search_request` share an id within one `search()`), so this is three sites rather than a source-wide problem.
